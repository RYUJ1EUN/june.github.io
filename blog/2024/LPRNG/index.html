LPRNG 구조 변화 분석

22.03.20 새로운 리눅스 커널 버전 5.17부터 LPRNG 변경

주요 차이점

속도를 고려한 변경으로 보임

  • 입력 풀 : 4092 → 256 비트 + fast pool
    • fast pool : 128비트 또는 256비트, CPU 코어 개수만큼
  • 출력 풀 → base CRNG + secondary CRNG
    • base CRNG : 256비트 1개
    • secondary CRNG : 256비트 CPU 개수만큼
  • 엔트로피 측정 방법은 변경되지 않음
새로운 LPRNG 구조

입력 풀의 구조

  • 해시함수 blake2s 사용 (가장 빠른 해시함수, MD 구조 아님)
  • 입력 풀의 내부 상태 갱신 함수는 blake의 update 함수를 그대로 사용
    • blake를 내부 함수로 사용
    • 즉, blake 자체가 pool로 사용됨

입력 풀에서 시드 추출 및 시딩 과정

  • 한 번 시딩이 이뤄진 후 keyed hash로서 사용됨
  • HMAC 자리에 대신 사용되는 것으로 보임
  • 256비트 value + CPU + cnt →[ hash ]→ 256 비트 value

base CRNG 구조

  • 내부 상태 : ChaCha20 스트림 암호 key로 표현됨
  • ChaCha20의 내부 상태는 512 비트이지만, 256 비트만 사용하고, 256 비트는 사전 정의 값으로 설정됨
  • 아무것도 안해도 60초마다 시딩이 이뤄짐

base CRNG에서 시드 추출 및 시딩 과정

  • secondary CRNG의 내부 상태 구조체는 base CRNG와 동일
  • base CRNG 출력 512 비트 중 상위 256 비트는 base CRNG의 새로운 키로 사용하고, 하위 256 비트는 secondary CRNG 시드로 전달
  • secondary CRNG의 개수만큼 시딩 동작
    • base CRNG처럼 60초마다 시드를 새로운 값으로 업데이트

난수 출력

현재 난수발생기와 동일한 동작

코어 간 동작에 영향 없음

  • 처음 사용자가 난수를 요청하면 256 비트 시드가 입력된 secondary CRNG의 첫 동작에서는 256 비트를 다음 요청에 사용하기 위한 키로 저장하고
  • 나머지 256 비트와 이어지는 동작으로 생성한 512 비트 난수들을 출력
  • 사용자의 다음 요청에는 이전 요청에서 생성한 키를 사용하며,
  • 첫 동작에서는 256비트를 다음 요청에 사용하기 위한 키로 저장하고 나머지 256 비트와 이어지는 동작으로 생성한 512 비트 난수들을 출력

fast pool

  • 내부 상태 : sipHash의 내부 상태와 동일
    • 가속화를 위해 작은 규모의 해싱을 반복하는 구조
    • 갱신 주기와 갱신 횟수를 저장
  • 내부 알고리즘으로 sipHash 함수를 호출하여 사용함
  • 기존 mixing function과는 조금 다름

입력 풀의 엔트로피 추정기(estimator)

  • 잡음원이 입력될 때마다 init_bits에 반영
    • 증가만 하고 감소 안 함
    • 한 번 엔트로피가 256비트에 도달하면, 이후 엔트로피가 떨어질 일이 없다고 간주하고 감소에 대한 부분을 관리하지 않는 것으로 보임
  • CRNG_EMTPY, CRNG_EARLY : 난수 요청 차단
  • CRNG_READY : 난수 요청 프로세스에 난수 공급

LPRNG 활용 잡음원

엔트로피 측정 방법

  • 사전 정의된 값을 엔트로피로 반영
  • 이벤트 발생 시간 차를 기반으로 엔트로피 측정

응용 프로그램에 따른 각 잡음원의 이벤트 또는 옵션 활성화에 대한 상태를 확인하고 실제 사용 빈도를 분석해야 함

latent entropy

  • 새로운 데이터를 혼합하더라도 증가된 엔트로피는 0으로 간주
  • 엔트로피 증가는 credit_init_bits 함수를 호출해야만 함
